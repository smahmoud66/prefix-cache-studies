# Independent mathematical and causality review

## State and exact reductions

I inspected the parent implementation in `../commitment_20261108/study.py`, its frozen configuration, report, summary and analysis code. I did not rerun its audit or replay. The following argument concerns ordinary leaf LRU with the declared request path protection, one fresh request touch per access and a fixed capacity and prefix dictionary.

Let a node denote its entire hash prefix. Its last-touch stamp is at most its parent's, since touching a node touches every ancestor. Every set of nodes with the same last touch lies on the single path accessed at that touch. Sort retained nodes from most to least recent by decreasing stamp and increasing depth (reverse canonical-ID order would complete a tie, but distinct nodes at the same stamp and depth cannot arise). Every ancestor now precedes every descendant. The last node is a leaf. Among eligible nodes it has exactly the legacy eviction priority of oldest stamp followed by greatest depth. For a new request, put its capacity-capped path first, from root child to tip, remove the old copies of its nodes, and append the surviving old order. While over capacity, the last node is an unprotected leaf because the protected path has length at most capacity. Removing the last node repeatedly is therefore the legacy eviction operation, including when a parent becomes a leaf. Truncation preserves prefix closure. Equal tuples consequently give identical hits, transitions and k-LPM continuation choices for any fixed request suffix, by induction. Absolute stamps, stamp-group boundaries, transient scratch and the elapsed count of service steps can be discarded for this LRU transition. Queue-aware eviction has a different priority rule and requires separate implementation.

For two actions with an identical exit tuple, every history rollout has identical cost, so the one with smaller immediate cost weakly dominates in the declared objective. If immediate costs also tie, retain the representative favored by the frozen action tie rule. A resident-set hash alone would invalidate this proof. When the value is identically zero, as for horizon zero or no complete pair, the immediate-search incumbent is itself optimal and is retained on ties. Replacing this rule by the first enumerated minimum can change the next cache even if the local cost is unchanged. The original immediate certificate bounds only the current work, and provides no such elimination of a distinct exit tuple. Mean historical continuation cost and immediate cost have the same units, whether represented in positions or by equivalent integer comparisons after cancellation of action-independent tails.

## Exact examples

All paths below have input length one more than their full-block extent, so each prompt accrues one common tail position. Each missing block costs 512 positions.

* **Identical residents, different future cost.** At capacity two, retain distinct single-block roots in MRU order `(a,b)` or `(b,a)`, attainable by serving the two roots in opposite orders. Apply singleton cohorts `c`, then `a`. In the first cache, `c` evicts `b`, and `a` hits, for one miss. In the second cache, `c` evicts `a` and `a` misses, for two. A comparison of resident sets would merge a 512-position difference.
* **Sacrificing an immediately optimal order.** At capacity two, start cold and complete singleton cohorts `a/x`, then `a/z`. This both initializes the retained path `a/z` and supplies one legitimate historical pair. The current chronological cohort is `[b/t, a/x]`. Serving `a/x` before `b/t` costs 1+2 misses and leaves `b/t`. The arrival order costs 2+2 misses and leaves `a/x`. The same historical pair costs 2+1 additional misses from `b/t` and 0+1 from `a/x`, respectively. Total two-cohort rollout objectives are 6 versus 5 misses, so the order with a 512-position immediate premium can win the causal objective. Actual subsequent demand could also be `a/x`, then `a/z`, realizing the 512-position net saving. Its occurrence on the two traces is a separate empirical question.

## Implementation inspection before evaluation

I read `engine.cpp`, `runner.py` and `contract.md`. The native engine traverses each permutation and stores a representative per complete ordered exit. The least immediate miss count wins within that class, then the original immediate incumbent and then chronological lexicographic order break ties. The same tie priority applies to the final integer-valued objective. For each independent historical sample, the value routine copies the exit and initializes a fresh k-LPM cycle in each of its cohorts. For history length h, its newest pair has chronological indices (h−2,h−1), then (h−4,h−3), up to eight pairs. H1 keeps the earlier cohort of each pair. Skipping rollout for one eligible exit changes only an action-independent constant. The implementation uses that shortcut only where the diagnostic does not require absolute future costs.

The driver reads the trace externally, then interns prefixes in chronological order only through the visible cohort. It groups and serves warm-up arrivals FCFS, initializes a bounded history separately per policy, commits each method's authoritative parent-simulator transition, and appends the current arrival-ordered cohort only afterward. Integer prefix names are opaque to the native optimizer. No method learns from another policy's service order. Ordinary LRU scoring is isolated from the queue-aware portfolio. The native online operation accepts the MRU tuple, current capped paths, immediate incumbent and at most 16 past cohorts. The separate diagnostic process receives two actual following cohorts only after the full online raw file is sealed. Online dispatch verifies the chosen order, its immediate cost and its complete resulting LRU tuple against the parent simulator on every decision.

The native source includes fixed counterexamples, zero-history and horizon-zero identities, finite pair indexing, random finite-trie comparisons against stamped leaf eviction, and invalid online-message checks. I inspected these tests without claiming an independent execution. Native per-decision scorer CPU excludes native parsing and reply serialization, which enter aggregate child process CPU. Counts of offered alternative states and comparisons of the actually selected and incumbent exits answer different questions.
