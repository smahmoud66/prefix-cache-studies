# When does request order matter for prefix reuse? Frozen CPU pilot, 12 November 2026

Decision: whether one **new** study earns GPU validation. Earlier reports and jobs remain closed. No new scheduler training, theorem search or accelerator use. A go is permission to propose validation, not a GPU measurement. Do not retune or acquire a replacement holdout after seeing results.

**Panel.** For every source select the first 5,000 requests in (actual arrival, stable source ordinal) order, with 2,000 unscored for capacity sizing and common FCFS warm-up; measure the following 3,000 without bin resets. Primary development: the exposed Mooncake conversation and tool/agent files. Secondary development: Qwen/Bailian chat and API, using the published project's lineage-isolated 512-token panel and its recorded parents. No random splitting of adjacent requests. One independent, previously unreplayed object: FreeInference coding/assistant gateway, CC BY 4.0, by Yiyu Liu, Minlan Yu and Juncheng Yang. Original times reflect their production environment; replay arrivals are exogenous, not new agent or GPU observations. Source: [dataset and attribution](https://huggingface.co/datasets/harvardMadsys/2026_prefixcache/tree/ba89a343a048073dda72617bb6087910da6214d0), [published layout](https://github.com/cacheMon/PrefixSim/blob/160d5f81724dd9ec28b10d6abb64615e6adbb332/doc/lcp_format.md). Verify all 75,971,550 compressed bytes, SHA-256 39f75bbba1ce912546517802719ef7742d0db7fa53dcbc66681bba090aa5d1f7. Scan the whole completion-sorted frame to select earliest **arrivals**. Never supply completion times, outputs or encoded next-access deltas to an online policy. Rebuild path IDs from ordered groups of 32 native 16-token blocks and every ancestor; isolate by released user ID, preserve recorded within-session order, respect in-panel parents. Replayed cache commits happen at modeled prefill completion. This reschedules an open stream; does not generate or infer future turns.

**Cache and service.** Same atomic prefix admission, LRU, 512-token blocks and eligibility horizon of 128 blocks as prior harness. Always charge the final token and any other uncacheable tail; eligible nodes are clipped to physical capacity. Changing cache size never changes input length. In the first 2,000 requests take the median distinct eligible node count over all 1,001 overlapping 1,000-request windows. For each ratio .10, .25, .50 or 1.00 round ratio × median to the nearest block (min one); keep C fixed across policies and time. Report realized ratio against the measured period's sliding-window median. These are counterfactual capacities, not four physical H100 configurations.

Time per request is a+bU+cUL milliseconds for original length L and uncached token count U. One nonpreemptive prefill stream; chunks of at most 4,096 newly computed tokens run consecutively for that request. Charge a once, accumulate b and c terms over chunks. Modeled TTFT is prefill completion minus scaled arrival. No decode, transport, batching across requests or observed user latency. The file calibration.json freezes the three nonnegative coefficients. Primary source: [NVIDIA AIConfigurator SGLang H100 SXM data](https://github.com/ai-dynamo/aiconfigurator/tree/6cd6f9686ab7de6e8fb28171d6e350ee0aa4ed39/aic-core/src/aiconfigurator_core/systems/data/h100_sxm). Batch-one FP/BF16 Qwen3-8B dimensions from [model config](https://huggingface.co/Qwen/Qwen3-8B/blob/b968826d9c46dd6066d109eabc6255188de91218/config.json); direct BF16 matrix and FA3 cold attention times × 36 layers; separate gate/up matrices. Fit nonnegative weighted least squares to cold-length component sums, excluding available reserved lengths among 128/1024/4096/12288. This is not an end-to-end profile; cache-hit extensions, long contexts, unfused operations and server overhead are not validated.

**Grid.** 3 offered FCFS utilizations (.60,.80,.95) × 3 ready caps (4,16,64) × 4 capacities = 36 primary cells per trace. Repeat as a sensitivity at W=2,000 ms; W=500 ms is the sole decision grid. At each capacity scale chronological arrival gaps by the common factor making FCFS service demand divided by first-to-last measured arrival span equal the target; no policy-specific rescaling. All requests finish. Reset only between cells. No benefit from waiting for future arrivals to fill the queue.

**Online policies and guard.** FCFS, adaptive resident longest-prefix match, oldest-first every k picks (k=2 or 4, reset at a dispatch group), deterministic prefix trie DFS. These are finite-queue adaptations, not instrumented SGLang. At dispatch take up to the first cap already-arrived requests and commit that group; releases during it become eligible at the following group. All methods preserve predecessor order. If serving the proposed request would put the oldest past its FCFS start + W, choose oldest now. Simulate the full proposed group and reject it if any start is infeasible. To protect an as-yet unseen suffix, reserve a worst-case cache debt before accepting a changed order; otherwise serve the group FCFS from its *actual* current cache. For each baseline resident block x, its first subsequent hit is safe if x is present in the proposed state and every block ahead of it there was ahead of it in the FCFS cache. Once touched in the common suffix, its rank is independent of initial state. Thus at most B_bad such blocks can add misses over the full fallback suffix. Require max(0, proposed_finish - FCFS_finish) + 512 B_bad (b+c Lmax) ≤ W, unless this is the final group. Lmax is the trace's scalar maximum input length, declared as an offline service envelope for all policies; no per-request future signal goes to an online policy. A rejected move need not be infeasible: this sufficient guard can suppress attainable gains. Check every actual start afterwards. No eviction rollback or free refilling.

**References and attribution.** E is the lowest full-episode service time among feasible existing policies incl. FCFS (retrospective best per cell). R_L is the better of E and a feasible LRU reference selecting among existing orders with a 16-request future rollout under LRU and the same guard. R is the best of R_L and the same candidate orders with full-future furthest-next-use retention; this protects the current path and discards farthest unused/deepest leaves, preserves ancestors and rechecks starts on the changed clock. Infeasible oracle variants are not candidates. Include LRU as a fallback, record the winning order/policy. I is infinite cache on **the winning R order**, the same finite warm contents, usable paths and mandatory tails. Use the same group release holds when retiming fixed orders. Report:
* G1=(FCFS−E)/FCFS, G2_mixed=(E−R)/FCFS, G3=(R−I)/FCFS, plus G2_order=(E−R_L)/FCFS and the incremental joint gain. Never call mixed G2 ordering-only. G3 is a fixed-order residual, not a proven global unavoidable penalty. Token-weighted work need not have an order-independent infinite-cache value because L varies.
* Primary work is total modeled prefill service milliseconds (no queue waiting); companion gaps use uncached input positions. All percentage gaps use FCFS within the same cell. Log p50/p99 nearest-rank modeled TTFT, every wait violation, actual depth and uncapped backlog. The oracle is feasible, not optimal. A weaker offline reference cannot rule out better schedules.
* Material ordering cell: G1 or G2_order at least 3% and its **achieving policy** has zero W violations and p99 ≤1.10 × FCFS p99. Also score the user's literal joint G1/G2_mixed rule with its corresponding p99 and a separate identical training procedure. A joint-only positive does not justify a scheduling claim.

**Prediction and stopping.** Only four inputs, all measured in a passive FCFS shadow without ordering outcomes: the fraction of queued eligible block occurrences shared with another ready request (first cap at each FCFS dispatch); nominal capacity ratio; median number of distinct intervening blocks on recurring positions in FCFS, divided by C (no reuse = sentinel); mean visible queue depth. Also log actual max and time spent at the cap (fraction of dispatches, not wall time). Select k on the two primary development workloads by lowest equally weighted primary-grid K/FCFS cost; prefer 2 on a tie. Secondary Qwen is diagnostic only. Fit a single-threshold rule on those same 72 development cells; try both directions on four features and constant predictions. Among rules of development precision ≥.8 maximize number of true positives then precision, stable feature/direction/threshold order on ties. No eligible positive rule means predict none. No weights or threshold fitting on test data. Hash the fitted rule, then produce and hash all 36 holdout flags from its FCFS-only shadow **before** opening test policy outcomes; one test scoring pass over both W values. Go only with ≥1 true flag and precision ≥.8 over primary flags. No flags: precision undefined, no go. Missed material cells: characterization only. No material attainable effect: stop investment here, not a theorem for other queues or services. The 36 grid cells share one traffic sample; precision is descriptive.

**Budget and verification.** Local CPU only, at most two workers and 172,800 CPU seconds. Per-process ceiling 8,000 CPU seconds and ≤12 numerical invocations. Clock, checksums, one-shot lock and full results preserved here. Check synthetic cache-debt proof cases, independent synthetic schedule/cost/TTFT reconstruction, and independently audit every start in the held-out primary LRU schedules using saved witnesses. Do not refit or run a second test grid.
